# Architecture overview (level 03 foundation)

The site is one Next.js 16 application. Every product feature is a **capability**
invoked through a single pipeline; every external system is a **provider** behind a
typed seam with a mock. The UI, the embedded AI concierge, and WebMCP tools are three
doors into the same room; none of them carries business logic or authorization.

## Layers and directories

| Layer | Directory | Rule |
|---|---|---|
| Contracts | `src/contracts` | Shared types and pure helpers. Dependency-free. Read-only for feature swarms (small, backward-compatible additions only, listed in the PR). |
| Capabilities | `src/capabilities` | One descriptor per action (`defineCapability`). Registered in `index.ts`. Never called by another capability's handler with a widened principal. |
| Policy | `src/policy` | Authorization, ownership, step-up, confirmation tokens. Pure functions; no I/O except the confirmation secret. |
| Domain | `src/domain/<feature>`, `src/db/repos` | Business rules and repositories. Talk to providers only through `@/providers/registry`. |
| Providers | `src/providers/<kind>` | External systems. `types.ts` (interface), `mock.ts`, concrete adapters, `index.ts` (mode selection). Leaves: never import domain, capabilities, or app code (lint-enforced). |
| Lib | `src/lib` | Env, logging, metrics, audit sink, idempotency, jobs, principal resolution, flags, redirects, crypto. |
| Data | `src/db` | drizzle schema (one file per table group), committed migrations, seed, client. |
| App | `src/app` | Routes only. Route handlers parse HTTP, resolve the principal, call `invoke`, map errors. No business logic. |

## Request lifecycle

1. `getRequestId` reads/creates a correlation id; every log line and audit row carries it.
2. `getPrincipal(request)` resolves anonymous / guest / admin through the installed `PrincipalResolver` (Better Auth, auth swarm). System principals are never derived from a request.
3. The capability route rate-limits per IP (`capabilityIp`, from `TRUSTED_PROXY_HOPS`-aware `getClientIp`) before reading anything, then resolves the principal, applies the CSRF check for signed-in callers (`assertSameOriginJson`), rate-limits per principal (or per IP for anonymous), and only then streams the body under a hard cap. The surface is always `ui` here; the concierge and WebMCP bridge build contexts server-side.
4. `createCapabilityContext` wires the database, audit sink, providers, readiness lookup, confirmation service, idempotency store, logger and metrics into `ctx.services`.
5. `invoke` runs the nine-step pipeline (see `capability-layer.md`) and always writes an audit row.
6. The route maps `CapabilityErrorCode` to HTTP via `HTTP_STATUS_FOR_CODE`, sets `Cache-Control: private, no-store`, and returns `{ ok, data | error, sources }`.

## Data

- Local: PGlite (embedded Postgres, WASM) in `./.data/pglite`; `memory://` in tests. pgvector loads from `@electric-sql/pglite-pgvector`; `db.vectorAvailable` reports whether it did.
- Production: Postgres via `DATABASE_URL` (postgres-js). Same drizzle schema and migrations.
- Migrations are generated by `drizzle-kit` into `src/db/migrations` and committed. CI fails if the schema and migrations drift.
- Level-03 tables: `site_settings`, `lifecycle_state`, `feature_flags`, `audit_events`, `jobs`, `metrics`, `content_sources`, `idempotency_keys`, `rate_limits`. Feature swarms add their own schema files and re-export them from `src/db/schema/index.ts`.

## Jobs

Durable queue in the `jobs` table (`src/lib/jobs`): `enqueue` (optional dedupe key), optimistic per-row `claim`, `complete`, `fail` with exponential backoff and a dead state, `reapStale`. Handlers register by type. Runners: the dev poller (`JOBS_INLINE_RUNNER`), `npm run jobs:run`, and `POST /api/jobs/run` behind `CRON_SECRET` for production cron. Handlers receive `ctx.db` (the runner's handle). The foundation registers one handler, `housekeeping.purge` (`src/lib/jobs/housekeeping.ts`): expired `idempotency_keys`, `rate_limits` idle for more than a day, `metrics` older than `METRICS_RETENTION_DAYS`. The cron route enqueues it with a dedupe key on every tick; at most one run per hour.

## Observability

- Logs: pino, JSON in production, pretty in development, redaction for otp/code/token/secret/email/phone/authorization/cookie.
- Metrics: counters and histograms buffered to a sink (console in dev, `metrics` table in prod, none in test). No third-party telemetry.
- Audit: append-only `audit_events` for every capability invocation (success, denied, failed) plus domain events (`AUDIT_ACTIONS`). Metadata is redacted with `redactForAudit`.
- Health: `GET /api/health` reports db driver, vector availability, lifecycle, and provider modes. Never values.

## Security posture

- Authorization is server-side only, inside the pipeline; hidden UI and omitted tools are never authorization.
- Guests see only what they are entitled to; ownership is re-checked by handlers with `assertActsFor`.
- Consequential actions need fresh sessions (`stepUp`) and signed confirmation tokens bound to the exact payload.
- Mutations are idempotent by key; replays return the stored response.
- External handoffs must pass `assertAllowedRedirect` (hyatt, CAA, uber, theknot, zola, withjoy, google/apple maps, opentable, resy, skyscanner, duffel, booking).
- Secrets live in server env only; `NEXT_PUBLIC_*` is the only client-visible configuration. `.env` is never read by agents.
- Legal gates (BIPA face matching, pro-media AI processing) are OFF by default and need both the env flag and a persisted readiness switch.
