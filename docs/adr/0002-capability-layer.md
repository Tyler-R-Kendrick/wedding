# ADR-0002: One capability layer shared by UI, embedded AI, and WebMCP

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-05 |
| Deciders | Tyler (integrator), design/SDLC swarm |
| Related | ADR-0001, ADR-0003, ADR-0004, ADR-0012, `docs/design/brief.md` §3.1–3.2, §3.6 |

## Context

Three surfaces act on behalf of a guest: the page UI, the embedded "Ask Us"
concierge (ADR-0003), and a WebMCP endpoint that lets a guest's own agent
read the schedule or draft an RSVP. If each has its own permission logic,
they drift, and the AI surface becomes the weakest one. Brief §3.6 ranks
"correctness and authorization" first.

## Decision

Every user-visible action is a **`CapabilityDescriptor`** registered once
and consumed by all three surfaces.

```ts
type CapabilityKind = 'read' | 'navigate' | 'draft' | 'action' | 'transaction' | 'external';

interface CapabilityDescriptor<I, O> {
  id: string;                      // 'rsvp.submit', 'travel.hotelBlock.open'
  kind: CapabilityKind;
  input: ZodSchema<I>; output: ZodSchema<O>;
  entitlement: (ctx: RequestContext, input: I) => Promise<Allow | Deny>; // server-side only
  confirmation?: 'none' | 'inline' | 'stepUp';   // required for action+, stepUp for transaction/external
  idempotency: 'none' | 'key';                    // required for action+
  lifecycle?: LifecycleState[];                   // ADR-0012 gate
  describe: (ctx) => ToolDescription;             // for AI + WebMCP
  run: (ctx, input) => Promise<O>;
}
```

| Kind | Examples | Confirmation | Idempotency |
|---|---|---|---|
| `read` | schedule, my table, hotel block details | none | n/a |
| `navigate` | open a route, deep-link a map | none | n/a |
| `draft` | prepare an RSVP, draft a message to the couple | none (drafts are not commitments) | n/a |
| `action` | submit RSVP, save dietary note, upload a photo | inline | key |
| `transaction` | redeem Uber voucher, reserve via provider | step-up (ADR-0001 §4) | key |
| `external` | hand off to registry, airline, hotel | explicit "Continue securely with <provider>" | key |

Rules:

1. **Entitlements run on the server**, inside `run`, against the
   `GuestAccessBinding` (ADR-0001). The UI, the AI tool list, and the WebMCP
   manifest may *hide* a capability; hiding is never the check.
   **Tool omission is UX minimisation, not authorization.**
2. The concierge and WebMCP see exactly the capabilities `describe`
   returns for the caller's context — never a superset, never an
   unregistered function.
3. `action`, `transaction`, and `external` require an idempotency key
   generated by the caller; replays return the original result.
4. `transaction` and `external` never execute from AI or WebMCP without a
   human confirmation step rendered by the UI; the AI may only produce a
   `draft` that the guest confirms.
5. Every invocation writes an audit row: capability id, caller surface
   (`ui` | `ai` | `webmcp`), binding id, idempotency key, outcome.
6. Capabilities carry the lifecycle states in which they are available
   (ADR-0012); out-of-state calls return a typed `Unavailable` result, not
   an error page.

## Consequences

**Positive.** One place to test authorization; IDOR tests are per
capability, not per surface. Adding an AI or agent surface adds zero new
permission logic. Audit is uniform.

**Negative / costs.** Boilerplate per capability. Some UI conveniences
(optimistic updates) must wait for the server. The `describe` output must
be maintained as carefully as copy.

**Follow-ups.** Capability registry with a generated table in
`docs/design/design-doc.md`. Contract tests that every route handler maps to
a capability. Self-review §2 is the enforcement checklist.

## Alternatives considered

| Alternative | Why not |
|---|---|
| Route-level middleware only | AI and WebMCP calls do not pass through page routes |
| Separate AI tool definitions | Drift; tool lists become an undocumented second permission model |
| Client-side gating | Trivially bypassed; violates principle 6 ordering |

## Compliance

- No server action or route handler outside `capabilities/` may touch the
  database: `grep -rn "db\." src/app` must be empty.
- Every `describe` output is snapshot-tested per role (anonymous, guest,
  household manager, admin).
